# Bug Record: BUG-2026-05-03-002

## Summary

- Title: Installer symlink replacement can delete existing user config targets
- Current status: `fixed-pending-verify`
- Severity: `high`
- Owner: dianedef
- Next command: `/sf-test --retest BUG-2026-05-03-002 on Termux device if available`

## Reproduction

- Preconditions:
  - A user has an existing real file or directory at a dotfiles-managed target such as `~/.config/starship.toml`, `~/.tmux.conf`, `~/.config/ranger`, or Termux equivalents.
- Steps:
  1. Run the installer path that calls `create_symlink <source> <target> false`.
  2. Let the helper replace an existing non-symlink target.
  3. Inspect the previous target.

## Expected Behavior

- Existing real files and directories are preserved by moving them to a backup path before the dotfiles symlink is created.
- Existing symlinks that already point at the requested source are left unchanged.
- Existing stale symlinks are replaced without recursively deleting real content.

## Observed Behavior

- `lib.sh:create_symlink` calls `rm -rf "$target"` when `backup=false`.
- `termux.sh:create_symlink` always removes an existing target with `rm -rf`.
- `install.sh:setup_configs` pre-backs up `~/.config/nvim` when it is a directory, which also catches symlinks to directories and makes repeated runs non-idempotent.

## Evidence

- `lib.sh` symlink helper used by the main installer.
- `termux.sh` standalone symlink helper.
- `TASKS.md` tracks the same issue as high-priority maintenance work.
